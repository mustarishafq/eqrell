# RCA — EQrel "points balances disappear the next day" (production)

Deployment: pwa-trial-cohort (eqrel.app) · DB: `pwa-trial-cohort-eqrel` · active run 7ef23491-e4da-493f-bb07-a569d7e48d68
Investigation = read-only Mongo + logs + pod events. **No data modified.**

## TL;DR
The production data is currently **internally consistent — no ongoing silent point loss is observable**. Every balance reconciles exactly to its transaction history (proof below). The ONE destructive, overnight-capable state-reset mechanism in the system is the server-start migration `points-economy-v1`, which **wipes every child's world to `tasik` only and zeroes `mataBinaSpent`**. It has run exactly once (2026-11-07 16:31 UTC) and will not repeat while its status is `done`. The reported "disappears the next day" symptom is explained by (a) the one-time migration effect that families saw once overnight, and/or (b) a **latent, dangerous design**: a destructive migration that executes on every server boot, guarded only by a `failed`/stuck status check, while the pod churns overnight (autoscaling + frequent redeploys). If that guard ever lets it re-run, it re-wipes worlds and re-zeros spent — exactly the reported failure mode.

## Root cause
1. **No ongoing silent loss exists in the data.** All balances reconcile exactly to claims/buildings. Whatever a child currently shows matches their verified-claim and spend history to the unit.
2. The only overnight-capable destructive mutation is the **`points-economy-v1` migration that runs on server start** and, when it runs, **wipes every world to `tasik` and sets `mataBinaSpent = 0`** (and recomputes mataReward). It ran once (Nov 7) — that single event is the most likely thing a family literally saw "disappear overnight" (their built world collapsed to a lake). It is currently dormant (`done`).
3. **Latent mechanism that reproduces the exact symptom:** the migration is destructive AND boots on every server start AND its re-run guard keys only on status `failed`/stuck. With overnight autoscaling pod churn + frequent redeploys, if the migration is ever left non-`done` (a crash/OOM/Mongo blip mid-run, or two pods racing the guard at boot before either writes `done`), it re-executes on the next boot and re-wipes worlds / re-zeros spent → balances/worlds "disappear the next day." This is a design-level data-loss hazard even though it has not triggered a second time yet.
4. Secondary, by-design: manual `belum` un-verifications subtract points (seen on Emierul's family Nov 8). If parents toggle verification, balances legitimately drop — a possible alternate explanation for a perceived "drop."

## Recommended fixes
- **Code (E1):** Harden `points-economy-v1` (and any boot-time migration) so it can never destroy already-migrated data:
  - Make the guard atomic & idempotent: claim the migration with a conditional update (findAndModify from "not-done" → "running" with a lock/owner + timestamp) so concurrent pod boots cannot both run it; treat `running`/`started` as in-progress (not re-runnable) rather than keying re-run on `failed` only.
  - Never blindly reset `mataBinaSpent=0`/wipe worlds on re-entry — gate the destructive reset behind a per-child "already migrated" marker (e.g. `child.preMigration` set / a `migratedAt`) so a re-run is a no-op.
  - Add explicit `[migration]` logging (start/skip/claim/complete) so future boots are auditable.
  - Prefer running one-time migrations as a gated job, not on every server start, given the pod autoscales and redeploys often.
- **User:** Confirm whether the family observed the loss (a) once around 2026-11-07 (the migration) or (b) repeatedly after specific nights/redeploys, and whether parents are using the un-verify (`belum`) action — this distinguishes the one-time migration from the latent re-run path and from manual un-verification.
